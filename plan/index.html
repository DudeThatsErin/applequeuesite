Overview

Apple Queue can be made public without turning dashboard.erinskidds.com into a shared multi-user backend.

The cleanest model is:

  • publish one browser extension,
  • publish one backend template,
  • let each user deploy their own backend,
  • use erinskidds.com as a guided setup wizard,
  • keep each user's queue data, secrets, and API usage isolated in their own deployment.

A strong option for the backend is a one-click Vercel deployment using a public template repository.

Recommended Architecture

Apple Queue
├── Public browser extension
│   └── Talks only to the user's backend
│
├── Public backend template repo
│   ├── Notes API
│   ├── Reminders API
│   ├── Calendar API
│   ├── Places proxy
│   ├── Queue storage
│   └── Blob attachments
│
└── erinskidds.com setup wizard
    ├── Choose modules
    ├── Choose defaults
    ├── Deploy to Vercel
    ├── Configure secrets
    ├── Configure extension
    └── Build iOS Shortcuts

The public website acts as the installer and setup experience. The user's own deployment acts as the backend.

1.Use a Bring-Your-Own-Backend Model

Instead of exposing your own Apple Queue APIs publicly for everyone, each user should deploy their own backend.

Their extension would talk to URLs such as:

https://my-apple-queue.vercel.app/api/apple-notes
https://my-apple-queue.vercel.app/api/reminders
https://my-apple-queue.vercel.app/api/calendar

Each deployment should use its own randomly generated API token.

This provides natural isolation between users and avoids making you responsible for:

  • multi-user account management,
  • queue isolation,
  • attachment storage for everyone,
  • rate limiting every user's traffic,
  • other users' AI costs,
  • other users' Google Places costs,
  • secret management,
  • abuse prevention,
  • operating a shared SaaS backend.

2.Create a Public Backend Template

Create a public repository specifically intended to be deployed by Apple Queue users.

It should contain the APIs needed for whichever modules are enabled:

  • Apple Notes
  • Reminders
  • Calendar
  • Google Places autocomplete
  • attachment upload/download
  • AI parsing, if enabled

Suggested configuration

Do not generate different source-code variants for every combination of features.

Use runtime configuration instead:

ENABLE_NOTES=true
ENABLE_REMINDERS=true
ENABLE_CALENDAR=false

DEFAULT_NOTES_FOLDER=Quick Notes
DEFAULT_REMINDER_LIST=Inbox
DEFAULT_CALENDAR=Calendar

The backend can expose an endpoint such as:

GET /api/config

The extension can use that response to hide modules the user did not enable.

This means you maintain:

  • one extension,
  • one backend template,
  • one setup wizard.

3.Replace Local Filesystem Storage for Serverless Hosting

The current implementation uses local files such as:

data/apple-notes-queue.json
data/reminders-queue.json
data/calendar-queue.json
data/uploads/

That works well on the Oracle server, but it should not be relied on for a serverless deployment.

For a Vercel-friendly version, use persistent hosted storage.

Queue storage

Possible options include:

  • Upstash Redis
  • Vercel-supported database integrations
  • Neon
  • Supabase

For Apple Queue's simple pending-item model, a small Redis/KV-style store is a natural fit.

Attachment storage

Use persistent object storage such as:

  • Vercel Blob
  • Cloudflare R2
  • Amazon S3
  • another S3-compatible provider

A Vercel-oriented template could use Vercel Blob by default.

4.Build a "Create Your Own System" Wizard

Create a page such as:

https://erinskidds.com/apple-queue/setup

The wizard should walk the user through their desired configuration before sending them into the deployment process.

Step 1 — Choose Apple Queue modules

What do you want Apple Queue to support?

☑ Apple Notes
☑ Reminders
☑ Calendar

Users can select any combination.

Step 2 — Choose defaults

Ask only for defaults relevant to the enabled modules. Examples:

Calendar

Step 3 — Optional features

Examples:

☑ AI natural-language parsing
☑ Google address autocomplete

If the user enables an optional feature, explain which provider account or API key is needed.

Step 4 — Deploy

Present a button such as:

Deploy My Apple Queue

That launches the deployment flow.

5.Use Vercel's Deploy Button Flow

Vercel supports template/deploy-button workflows where the user can:

  1. log into Vercel,
  2. clone the template into their own source-control account,
  3. create a Vercel project,
  4. configure required environment variables,
  5. deploy the application,
  6. return to your site afterward.

Your setup page can prepare non-secret defaults before deployment. Examples:

ENABLE_NOTES=true
ENABLE_REMINDERS=true
ENABLE_CALENDAR=true
DEFAULT_NOTES_FOLDER=Quick Notes
DEFAULT_REMINDER_LIST=Inbox
DEFAULT_CALENDAR=Calendar

Do not put sensitive values directly in a public deployment URL.

Secrets should be requested during deployment or entered afterward. Examples:

APPLE_QUEUE_API_KEY=...
OPENAI_API_KEY=...
GOOGLE_PLACES_API_KEY=...

6.Generate a Strong Per-Installation API Key

Each deployment should have its own Apple Queue API token.

For example, generate a cryptographically random value and store it as:

APPLE_QUEUE_API_KEY=<random-secret>

The extension then stores:

Server URL:
https://users-project.vercel.app

API Key:
••••••••••••••••

The backend should require that token for:

  • queue creation,
  • pending queue reads,
  • acknowledgements,
  • deletes,
  • protected configuration endpoints where appropriate.

Never ship the Google Places or AI-provider secret key in the extension.

7.Make the Extension Backend-Agnostic

Do not create a separate extension ZIP for every user. Use one public Apple Queue extension.

On first run, show a setup screen such as:

[ Test Connection ]

After the server URL and API key are saved, the extension can call:

GET /api/config

and configure itself automatically. This greatly simplifies future extension updates.

8.Redirect Users Back to erinskidds.com After Deployment

After the backend deploys successfully, send the user back to the setup wizard. The return page can continue with:

Your Apple Queue backend is ready.

Backend:
https://my-apple-queue.vercel.app

Next:
1. Install Apple Queue
2. Add your server URL
3. Add your API key
4. Test the connection
5. Configure your iOS Shortcuts

Ideally the deployment flow provides enough information to prefill the backend hostname or otherwise help the user copy it.

9.Browser Extension Distribution

For a real public release, use the official browser extension stores instead of asking ordinary users to work with development-mode ZIP files.

Chrome

Recommended:

  • publish Apple Queue in the Chrome Web Store,
  • let users install it normally,
  • configure their backend URL and API key afterward.

For development/unpacked installs, Chrome normally requires:

chrome://extensions
→ Developer mode
→ Load unpacked
→ Select extracted extension folder

Users should not be told that a normal ZIP can always be dragged directly onto the Chrome extensions page.

Firefox

Publish/sign the Firefox version through Mozilla Add-ons where possible. A public signed extension gives users a much smoother experience than temporary unsigned development installs.

10.Explain Local Files vs. Hosted Backend Clearly

If users use the Vercel/serverless version, they should not need to keep the backend project files running on their personal computer.

The extension depends on the hosted backend, not a local copy of the source files.

If you also provide a self-hosted/local option, explain the difference explicitly.

Hosted option

Your backend runs on Vercel.
Your computer does not need to stay on.

Self-hosted option

Your backend runs on your own server
or computer. That system must remain
available for Apple Queue to work.

Do not mix those instructions.

11.Google Places Autocomplete

If Google Places is enabled, the browser extension should call the user's backend:

Extension
   ↓
/api/places/autocomplete
   ↓
User's backend
   ↓
Google Places API

The Google key stays only in the backend's environment variables:

GOOGLE_PLACES_API_KEY=...

This prevents distributing the key in extension source code.

Rate-limit this endpoint and debounce client requests to reduce unnecessary usage.

12.AI Parsing

Treat AI the same way. The extension should never contain the user's AI-provider secret.

Recommended architecture:

Extension
   ↓
User's backend
   ↓
AI provider

Allow AI to be disabled entirely:

AI_ENABLED=false

If enabled, the deployment flow can ask the user for the required secret.

13.Attachment Handling

For public deployments, move attachment storage away from the deployment filesystem.

Recommended flow:

Extension
   ↓
POST /api/apple-notes/upload
   ↓
Persistent object storage
   ↓
Public or protected attachment URL
   ↓
iOS Shortcut

Keep two filename concepts separate:

Display name:
bowen_img.jpg

Storage identifier:
randomized-identifier-bowen_img.jpg

The queue item should preserve the original display name while storing a durable retrieval URL.

14.Security Requirements

Before releasing publicly, ensure each deployment follows these rules:

  • generate a strong random Apple Queue API token,
  • require authentication for queue operations,
  • do not put Google or AI keys in browser extension code,
  • rate-limit endpoints that proxy paid APIs,
  • validate upload sizes and MIME types,
  • use persistent object storage for attachments,
  • sanitize filenames,
  • prevent path traversal,
  • validate all request bodies,
  • restrict provider API keys where possible,
  • keep secrets only in server-side environment variables.

15.Vercel Free-Tier Caveat

Do not market the deployment as guaranteed to be free forever. Vercel's pricing, quotas, and terms can change.

The Hobby tier may be a good fit for personal/open-source deployments, but users should be told that:

  • they own their Vercel account,
  • they are responsible for provider usage,
  • storage/database/API providers may have their own limits,
  • paid upgrades may eventually be required depending on usage.

Use wording such as:

Apple Queue can usually be deployed using free-tier services for light personal use. Provider limits and terms may change, and you are responsible for usage on accounts you connect.

17.Suggested Development Phases

Phase 1 — Separate configuration from code

Add:

/api/config

and environment-driven module/default configuration. Make the extension dynamically show enabled modules.

Phase 2 — Replace filesystem queues

Move Notes, Reminder, and Calendar queue persistence into a serverless-safe datastore.

Phase 3 — Replace attachment filesystem storage

Move attachment files to Blob/R2/S3-compatible storage.

Phase 4 — Create backend template

Create a standalone Apple Queue backend repository designed for user deployment.

Phase 5 — Build setup wizard

Create the guided flow on erinskidds.com.

Phase 6 — Add deployment integration

Connect the wizard to a Vercel deploy-button/template workflow.

Phase 7 — Make the extension universal

Add first-run setup, connection testing, /api/config, and backend-independent settings.

Phase 8 — Publish browser extensions

Release through:

  • Chrome Web Store
  • Mozilla Add-ons

Phase 9 — Improve onboarding

Create guided Shortcut setup instructions for each enabled module. Only show instructions for modules the user selected.

18.Recommended End State

The user should feel like they are installing a product, not cloning a development project.

The ideal experience is:

Choose what you want Apple Queue to do, deploy your private backend, install the extension, connect it, configure your Shortcuts, and start using it.

Your infrastructure

  • documentation,
  • the setup wizard,
  • the extension distribution,
  • the template repository.

The user's infrastructure

  • their queues,
  • their attachments,
  • their API secrets,
  • their AI usage,
  • their Places usage,
  • their Apple Queue API endpoint.

That gives Apple Queue a realistic path to being public without requiring you to operate a full multi-tenant SaaS backend.
